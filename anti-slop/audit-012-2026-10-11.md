# Admin and developer settings performance audit

Scope: Settings (including LLM Engine and CLI/API), admin Users, and admin Security. The user authorized the audit and fixes. Existing profile/setting separation, dark surfaces, green accent, and badge treatment are preserved. Antislop is the final check, as previously requested.

## Findings and implemented fixes

1. Settings fetched projects, tokens, and admin LLM configuration on entry, regardless of the selected tab. Token and LLM reads now start only on their respective tabs; settings project summaries load only when needed for token scoping. Successful reads are retained during tab navigation, preserving edited provider drafts. Cancelled requests cannot overwrite data after leaving a tab. LLM loading/failure states prevent saving an empty configuration after a failed read and provide retry.
2. AccountWorkspace issued an extra /api/me request despite getCurrentUser already resolving it. This request was removed. The auth hook no longer invalidates its initial identity resolution on INITIAL_SESSION. Global display synchronization defers to the account settings hook on Profile and Settings instead of fetching the same preferences twice there.
3. /api/me called getAccountDetail, which read full subscription history and counted usage and projects. GET identity now uses getAccountSummary: one database query selecting identity and currently valid membership. It does not need usage totals. Account name validation and banned-account checks remain in PATCH. Expired or ended subscriptions are excluded from effective membership; detailed billing operations still synchronize subscription history.
4. listAccounts had an N+1 loop: a users query plus expiry and subscription reads for every user. It now selects users and active subscriptions in one query, chooses the newest active period, and preserves Free/Pro, indefinite membership, bans, admin labels, search, and date ordering. Users renders 25 rows per page with next/previous navigation. Search reads cancel older requests.
5. Security awaited independent database reads sequentially and made external geolocation part of the response path. Independent reads now run in parallel; the 24-hour total comes from the same by-type counts rather than a duplicate count query. Email lookup covers both recent events and the top-account list. Location lookup runs after the response, uses an hour cache for successes and a short cache for failures, and merges simultaneous lookups for an IP. Location is optional and may appear on a later refresh of a warm instance. Fast filter changes cancel superseded reads.
6. Eager imports pulled profile, project, account-panel, and sidebar code into unrelated settings pages. These components now load separately when rendered. Existing server authorization remains in place; no protected configuration is cached publicly or exposed to non-admin users.

## Evidence

- Production Settings client dependency chunks: 1,019,094 raw bytes / 285,215 gzip bytes before; 701,830 raw / 182,402 gzip after. Approximately 36% less gzip data. Measurement unions client-reference manifest chunk paths, excluding deferred profile/project/account-panel/sidebar entries; the baseline used the same filter. This is a bundle comparison, not a promise of an equivalent page-load speedup.
- Read-only configured-database check, 34 accounts: listAccounts used one query in 118 ms, versus the previous code's minimum 69 queries for 34 users. getAccountSummary used one query in 87 ms. These are individual local observations, not production percentiles or a load test. No account contents or credentials were printed.
- 96 tests pass, including active/expired/ended/indefinite membership and geolocation concurrency/failure behavior. Production build and TypeScript pass. Scoped ESLint has no warnings or errors. Two pre-existing CSS optimizer warnings remain.
- Anonymous requests to /api/llm-config, /api/admin/users, and /api/admin/security, including a client-supplied admin identity, return 401.
- Browser preview verified provider input, tab navigation, retained draft values, security filter/pagination controls, and no settings console errors. No actual provider configuration, subscription, IP block, or credential was changed. Screenshot: artifacts/admin-performance-settings.png. Authenticated production admin interaction was not benchmarked.

## Final antislop check

No additional blocking design findings. R-04/R-29: existing account categories and single green visual direction remain consistent. R-32: provider inputs and icon buttons now have accessible names; loading, error, and retry are visible. Reviewed English/Indonesian labels cover the changed controls and common admin table labels without translating user content. R-37: ENERGY 2, RHYTHM 2, MOTION 2; existing reduced-motion handling is preserved. This performance release does not redesign the admin pages or complete the unrelated 72-point PRD work.

Remaining scale limit: admin Users still retrieves the complete matching account list; pagination limits DOM rendering, not the response size. Server-side pagination should be added if the account population grows substantially. External geolocation and database/network latency can still vary. No claim of handling millions of concurrent visitors is made.
